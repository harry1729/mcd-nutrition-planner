## 一、先做归因：昨天群发为什么没用

不是"发得不够多"，是**三个结构性错误**。

### 错误 1：找错了人

你的好友群 = 微信社区 = 普通消费者 / 非程序员。  
**他们不会为了一个"还不错"的项目去注册 GitHub 账号。**

数据佐证：

- 头部项目 `mcd-party-planner`：874 Star / 52 Fork / **124 Watcher**  
  → Watcher 才是真正"关注"的人，说明它触达的是**开发者**
- 你的仓库：1 Star / 0 Fork / 0 Watcher  
  → 一个技术社区的人都没触达

**Star 的主力来源是技术社区，不是微信群。**

### 错误 2：撞了登录墙，还以为是"吸引力不够"

实测：未登录状态访问 GitHub 仓库页，页面上有 **7 个 `/login?return_to` 链接**。  
点 Star → 跳登录 → 注册 → 验证邮箱 → 才能点。

对一个只想帮忙点一下的人来说，这条路径有 **5 步**。转化率必然极低。

**这一条无法绕过**（GitHub 的规则），只能：

1. 降低"要注册"的突兀感 → 落地页加「30 秒看懂」预热（已做）
2. **只找已经有 GitHub 账号的人** → 这是最有效的解法

## 二、坑 1：Token 少一个 Bearer，403

从控制台复制的 Token 直接粘进去，服务端返回 403「校验鉴权 authToken 必填」。

翻官方 README 才发现要求是 `Authorization: Bearer <token>`，
**少了 `Bearer ` 前缀**。麦当劳 MCP 和大多数国内 MCP 服务不一样，
这个坑文档里没明说，只能自己撞。

## 三、坑 2：详情接口根本不返回价格

最大的意外。`query-meal-detail` 只返回 `code / name / rounds / image / supportModify`，
**没有任何价格字段**。

一开始以为是没传对参数，反复试了几次。翻文档才发现——
价格本来就该用 `calculate-price` 算，因为含实时优惠，
不可能从静态商品详情得出。

这直接改变了架构：从「逐个查详情」改成「批量计价」。
107 个餐品分 9 批算完，顺带发现有些餐品原价 24 元、优惠后 15.9 元，
这种信息只有计价接口才拿得到。

## 四、坑 3：营养数据是纯文本，不是 JSON

`list-nutrition-foods` 返回的是这样一坨：

    中薯条,null,1210,289,4,12,38,165,18
    巨无霸,null,2146,513,27,26,42,961,171

6000+ 行的 CSV 风格文本，描述字段常为 `null`。

刚写完 JSON 解析器发现不对，拆开才看到真实结构是
`{ success, code, data: "<纯文本>" }`。最后按「末尾 7 个数字对齐」解析，
拿到 158 条营养数据。

**教训**：不要假设 MCP 返回的一定是 JSON 结构化数据。

## 五、坑 4：求解器把 3 元酱料包选成 20 人主食

这是最尴尬的一个 bug。

20 人、预算人均 40，跑出来的方案是：

    · 韩式烟熏芝士风味酱
      20 份 × ¥3.00 = ¥60.00

人均 3 块。技术上「最优」——预算内、份数精确、营养达标（因为营养数据
匹配不上，按 0 计算还"达标"了），业务上荒谬。

根因有两个：没按分类语义剔除非主食商品；营养匹配失败时按 0 处理，
反倒成了"达标"。

加了 `isMainCourse()` 按真实分类判定，修复后同一场景的输出是：

    · 芝士安格斯厚牛堡
      20 份 × ¥31.50 = ¥630.00
      696 kcal / 蛋白质 32g / 钠 897mg（人均）
      MCP calculate-price 复核：一致 ✓

## 六、算法：优惠券分配的背包 DP

团餐的券分配是道挺有意思的题：单笔订单通常只能用一张券，但拆单可以叠加。
怎么在「每张券的门槛金额必须被真实订单覆盖」的前提下求最大优惠？

用二维 0/1 背包：`dp[cost][n]` = 投入门槛金额 cost 元、用 n 张券时的最大优惠。
关键是约束 `cost ≤ subtotal`——这保证每张券都绑定一个真实覆盖门槛的订单，
杜绝优惠凭空叠加。

实测 480 元订单：

- 贪心（按门槛从高到低切）→ 优惠 100 元
- 背包 DP → 优惠 125 元（满300减100 + 满100减25，2 单）
- 再拆第 3 单需 ≥700 元额度，不可行 → **数学上可证最优**

还有个反直觉的点：**折扣券不适合拆单**。折扣券按订单总额比例减免，
拆单反而降低可用额度，最优用法必然是整单使用。
所以拆单分支只考虑满减券，这样金额还能精确到分。
