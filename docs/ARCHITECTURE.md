# 架构说明

## 分层设计

```
┌─────────────────────────────────────────────┐
│  CLI 层        src/index.js                  │  参数解析 / 模式切换
├─────────────────────────────────────────────┤
│  编排层        src/mcp/orchestrator.js        │  MCP 调用编排 + 链路追踪
│                     │                │
│                 ┌───┴────┐           │
│                 │        │           │
│  适配层   adapter.js   client.js      │  数据归一化 / JSON-RPC 传输
│                 │        │           │
├─────────────────┴────────┴───────────┤
│  求解层        src/solver.js                 │  ★ 纯函数，无网络依赖
│  模型层        src/model.js                  │  领域模型与约束定义
└─────────────────────────────────────────────┘
```

**关键设计**：求解层不依赖任何上层。这使得全部决策逻辑可以用 45 个单元测试完全覆盖，
评委无需 MCP Token、无需网络即可验证项目核心价值。

## 数据流

```
MCP query-meals ──┐
MCP list-nutrition├─▶ adapter.normalize──▶ 归一化 MenuItem[]
MCP query-store-coupons ┘
MCP available-coupons ──▶ adapter.normalize ──▶ 归一化 Coupon[]
                                 │
                                 ▼
        solver.solveCateringPlan(menu, coupons, input)
                                 │
            ┌────────────────────┼────────────────────┐
            ▼                    ▼                    ▼
        Plan (best)Plan[] (all)      diagnostics
            │                             │
            ▼                             ▼
        render.js                     报告 / 自检
```

`adapter.js` 的存在意义：MCP 返回的字段名可能随服务端版本调整。
求解层不应感知这些差异，因此所有映射收敛在适配层。

## 关键设计决策

### 1. 零依赖 MCP 客户端

**决策**：手写 JSON-RPC 2.0 over Streamable HTTP，不引入 `@modelcontextprotocol/sdk`。

**理由**：本项目主张"clone 即可运行"。若引入 SDK，评委可能因安装失败而无法验证。
手写客户端约 200 行，同时反而能精确控制 session 协商、限流处理、SSE 兼容等细节。

**代价**：需要自行处理协议演进。项目已在代码中标注协议版本与规范出处。

### 2. 求解逻辑本地化

**决策**：菜单与券来自 MCP，但"怎么选"完全由本地确定性算法决定。

**理由**：企业决策需要**可解释、可复现、可审计**。模型黑盒决策无法向财务解释
"为什么选这个不选那个"。同时本地算法可被测试覆盖，而模型输出无法穷举验证。

**表现**：每个被剔除商品记录剔除原因，每个方案风险有对应警告。

### 3. 打分目标非"最便宜"

**决策**：预算符合度权重仅 0.25，营养质量（蛋白）占 0.25，份数与钠各占 0.15。

**理由**：开发首版以省钱为主导向，导致 1020 元订单被拆出 970 元优惠、
人均 2.5 元的荒谬结果——技术上"最优"，业务上不可接受。
企业团餐的价值是"预算内让 20 个人吃好"，不是"尽可能少花钱"。

**修正后的得分函数**：

```
score = 0.25·预算符合度 + 0.20·蛋白达标 + 0.15·钠控制
      + 0.15·份数覆盖 + 0.25·营养质量
```

### 4. 券分配用二维 0/1 背包

**决策**：不用贪心，采用 `dp[cost][n]` 二维状态。

**理由**：贪心按门槛从高到低切分会浪费组合空间。实测 480 元订单：

- 贪心结果：优惠 100 元（仅用满300减100）
- DP 结果：优惠 125 元（满300减100 + 满100减25，2 单）

**核心约束**：`cost ≤ subtotal`。这是数学上证明优惠不会虚高的关键——
每张券的门槛金额都被真实订单覆盖。

**拆单仅考虑满减券**：折扣券按总额比例减免，拆单降低额度，最优用法必然是整单使用。
排除后可保证拆单金额精确到分，避免 135.45 这类零碎小数。

## 可扩展方向

| 方向 | 说明 |
|------|------|
| 多人口味偏好 | 引入偏好权重矩阵，按不同人群比例分配餐品 |
| 历史数据分析 | 结合 `order-list` 分析既往订单，优化复购策略 |
| 主题活动衔接 | 接入 `query-party-*` 系列工具，团建场景一键预约 |
| 积分兑换决策 | 接入 `mall-*` 工具，评估积分抵扣与现金支付的优劣 |
| 报告导出 | 支持导出 Markdown / PDF，便于会议前分发 |

## 测试策略

45 个单元测试分布在求解层与适配层，按关注点分组：

| 分组 | 覆盖内容 |
|------|---------|
| 输入校验 | 人数非法、预算非法 |
| 硬约束 | 过敏原过滤、标签过滤、饮品误作主食 |
| 主食判定 | 真实菜单分类识别、酱料包排除、名称启发式回落 |
| 份数计算 | 向上取整、servings>1 场景 |
| 券逻辑 | 门槛未达不生效、过期券过滤、次数上限 |
| 拆单优化 | 拆单优于单单、份数上限、折扣整数性 |
| 降级路径 | 预算不足标记、全员过敏不可行 |
| MCP 字段兼容 | 4 种字段命名变体、4 种容器结构、折扣率归一化、缺字段回落 |
| 营养表解析 | 纯文本 CSV 对齐、跳过非法行、多层嵌套剥壳 |
| 响应解析 | structuredContent 优先、JSON 解析、非 JSON 降级、空输入 |

其中"折扣整数性""拆单上限""折扣率归一化""酱料包作主食""营养表解析"五条用例，
都是在真实联调中实际发现 bug 后补写的回归测试。
这五条都属于"MCP 返回值形态与直觉不符"类问题——单元测试的价值正在于此。
